# State Management Guide

## 목표
- MVP는 단순하게 유지하되, 서버 상태와 로컬 UI 상태를 혼합하지 않는다.
- 모든 화면이 같은 fetch 패턴을 사용하도록 통일한다.

## 기본 원칙
- 로컬 상태(Local UI State):
  - 입력값, 모달 열림/닫힘, 임시 선택값 등 화면 전용 상태.
  - 수명주기: 화면 단위.
- 서버 상태(Server State):
  - 사연 목록/상세, Top10, 투표 잔여, 제출 상태 등 원격 데이터.
  - 수명주기: 요청-캐시-재검증 흐름.

## 단일 데이터 페칭 패턴
- 패턴 이름: `Feature Query + Contract Mapper`.
- 규칙:
  1) 화면(`app/*`)은 직접 fetch하지 않는다.
  2) `features/*/api`에서만 API를 호출한다.
  3) 응답은 즉시 mapper로 앱 내부 타입으로 변환한다.
  4) UI는 `loading/success/error/empty` 상태를 공통으로 사용한다.

## 권장 흐름
1. Screen -> Feature Query 함수 호출
2. Query 함수 -> `lib/api/client`를 통해 Supabase/RPC/Edge 호출
3. 응답 -> `lib/api/mappers`로 정규화
4. 캐시 저장 -> 화면 렌더
5. 포그라운드 재진입/수동 새로고침 시 재검증

## 리스트 캐싱 전략

## 사연 목록 (`stories`)
- 키: `stories:list:{cursor|filter}`
- TTL 권장: 30~60초
- 정책:
  - 초기 진입 시 캐시 있으면 즉시 렌더 후 백그라운드 재검증
  - 작성 성공 후 목록 캐시 invalidate
  - 차단/삭제 반영 필요 시 강제 재조회

## 곡/결선 목록 (`songs`, `final_tracks`)
- 키: `show:top10`
- TTL 권장: 15~30초 (투표/순위 반영 빠르게 체감)
- 정책:
  - 재생 시작 전 상세/URL은 별도 요청
  - 투표 성공 시 `show:top10` 및 `votes:remaining` 동시 갱신

## 쓰기(Mutation) 처리 규칙
- 사연 작성, 투표, 신고, 제출 완료는 모두 서버 함수를 통해 실행.
- 클라이언트 낙관적 업데이트는 제한적으로 사용:
  - 투표: 성공 응답 전 카운트 확정 금지
  - 사연 작성: 성공 시점에만 목록 반영
- 모든 mutation은 표준 에러 객체로 UI에 전달한다.

## 오프라인/실패 처리
- 읽기:
  - 캐시가 있으면 표시 + 오프라인 배너.
  - 캐시가 없으면 에러 화면 + 재시도 버튼.
- 쓰기:
  - 네트워크 단절 시 즉시 실패 처리(자동 무한 재시도 금지).
  - 사용자가 명시적으로 재시도하도록 유도.

## 일관성 규칙
- 권한 관련 상태(`role`, `entitlement`, `remainingVotes`)는 서버 응답이 진실이다.
- FE의 파생 플래그는 표시용이며, 허용 판정은 서버에서 다시 검증한다.
- 타입 불일치가 발생하면 mapper 단계에서 실패시키고 UI에 안전한 메시지를 보여준다.

## 도입/변경 제약
- 새 라이브러리 도입은 정당화와 문서화가 있어야 한다.
- 상태관리 라이브러리 도입이 필요하면 먼저 티켓으로 제안하고 계약 문서 영향도를 명시한다.
